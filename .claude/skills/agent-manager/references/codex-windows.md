# Which window a Codex thread is in

Read before changing `Core/Codex/CodexSource.cs` or `CodexWindows.cs`, or when a Codex card raises, sends to or closes the wrong window.

Codex's app-server daemon runs every window's threads and holds every rollout open, and Codex records which window shows a thread nowhere (not the rollout, the lock files or its databases). A wrong window sends Raise, Send and Close to someone else, so no answer beats a guess.

- **The daemon is never a window.** `CodexWindows.Daemons`: a Codex process whose parent is Codex, the process in `app-server-daemon/daemon.pid`, or one whose first argument is `app-server` (a helper that outlives its parent). Taking one for a window hands one card between two windows' threads each scan and gives the daemon's pid to Raise and Close.
- **Placing a daemon-hosted thread**, in order: the window whose command line resumes it (`WindowResuming`, read with `ProcessTable.CommandLine`; the manager's Resume and Restore start windows this way); the window started within `STARTUP_MATCH` with the thread's first prompt on its command line (`WindowPrompted`, because `astra.py` opens several windows in one second); else the newest window started within that time, for that window's first thread only (`FirstThreadOfEachWindow`). A window started to resume opens no thread and is left out of both start-time matches.
- **`/clear`, `/new` and a picked `/resume`** leave nothing on disk. `WindowShowing` reads each window's screen through `ConsoleInput.Attached` (read-only), compares letters and digits only (the TUI wraps, indents and strips markdown), and needs one clear winner; it runs only while an unplaced thread exists, at most every `SIGHT_RETRY`. `PlaceOnWindow` then takes over the card of the thread that window showed (`TakeReplacements`). A thread no screen shows has no window; with no Codex window open it counts as closed.
- **Liveness:** a thread is alive while a `codex.exe` holds its rollout (`FileHolders`, the Restart Manager). `FileHolders.Pids` returns null, never an empty list, when it could not ask, and a null keeps what the thread had. Each query walks every handle on the machine, so `IsKnownNotHeld` skips it while the Codex processes and the last event are unchanged, and a held rollout keeps its holder (`HeldUnder`, `KnownHolder`) until the Codex processes change or `NOT_HELD_RECHECK` passes. The daemon keeps a thread for a while after its window closes, so `IsGone` closes a thread whose remembered window (`LastWindow`, pid and start time) has exited.
- **A window nothing was typed into** writes no rollout, index line or database row. `FindEmptyWindows` gives an interactive window (`IsInteractive`: no subcommand, or `resume` / `fork`) not started to resume a `New Codex` card keyed by `EmptyWindowKey`, while no thread has been placed on it; the first thread placed on it takes that card, so it keeps its spot.
- **One orchestrator owner for all of them:** Codex runs shell commands inside the daemon, so every Codex window is the owner `codex:<daemon pid>`. The manager maps that owner to no card while two Codex threads are alive, so lane and task signals reach a Codex card only when one is alive, and `Delivery.Plan` never sends a Codex through the inbox. On a bridge channel the peer is the Codex thread whose own commands used the channel (`AgentHub.CodexThreadOn`, `BridgeRules.MentionedChannels`).
